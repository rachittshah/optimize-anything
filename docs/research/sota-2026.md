# SOTA for reflective text optimization (Nov 2026) and the optimize-anything upgrade

Date: 2026-11-11 · Branch: `sota-upgrade` · Inputs: 7 independent expert trees + 1 agent-config probe (§2).
**Citation rule:** every claim has a URL or a tag: `unverified`, `estimate`, `abstract-only`, `secondary`, `search-hit` or `author-reported`. All numbers come from the reports. When two trees tagged a source differently, the weaker tag is kept.

## 1. Summary
- **SOTA per these reports.** GEPA-style reflective mutation with per-example Pareto selection is still the reference loop.
  - Pareto beats SelectBest: +12.44 vs +6.05 gain ([GEPA v2](https://arxiv.org/html/2507.19457v2)).
  - GEPA beats GRPO: 54.85 vs 48.91, using 1.8k–7k rollouts vs 24k (same source).
- **2026 gains came from discipline more than from search power.**
  - RLMOpt adds significance-gated promotion and wins on held-out data, 0.610 vs 0.589 ([2608.10471](https://arxiv.org/html/2608.10471v1)).
  - SEPO's local edits give +2–3pp (`abstract-only`, [2608.28067](https://arxiv.org/abs/2608.28067)).
  - ASI raises test score from 82.5 to 86.32 ([OA paper](https://arxiv.org/html/2605.19633)).
  - SkillOpt (shipped code) adds an edit budget and a rejected-edit buffer (T7).
- **Where the budget goes:** validation dominates ([GEPA v2](https://arxiv.org/html/2507.19457v2)), and racing beats uniform allocation by ~15% ([TRIPLE](https://arxiv.org/html/2402.09723v3)).
- **Judges are the weak point.** A 3-judge ensemble still passed 55% of bad answers; a commit-first judge cut the false-positive rate from 0.719 to 0.012 ([2607.05904](https://arxiv.org/abs/2607.05904)).
- **Adopted:** U1 GEPA-faithful core + eval hygiene (with feasibility gate and exact output cache) · U2 held-out split + paired promotion · U3 paired successive halving · U4 cost-aware routing + lean judge · U5 portable agent interface.
- **Run as A/B (flag, off by default):**
  - operator-portfolio bandit (section-edit and merge arms)
  - counterexample mining (train/dev only)
  - SPRT racing
  - rejected-proposal memory
  - edit-size budget
  - parallel eval
  - repeated judge evals
  - pairwise gate
- **Rejected:** weight RL, best-of-N as a search method (kept as a bench baseline), cheap reflector as default, QD archives, UCT, annealing.

## 2. Method
| Symbol | Definition |
|---|---|
| **N** (axes) | Started with 6: (1) search strategy · (2) selection · (3) feedback signal · (4) model routing · (5) budget control · (6) artifact scope. **Expanded to 20:** (7) acceptance/promotion · (8) eval hygiene · (9) edit granularity · (10) split discipline · (11) judge design · (12) interface/packaging · from T6: (13) training-set growth · (14) operator portfolio · (15) pre-screening · (16) candidate rating · (17) memory across runs · from T7: (18) proposal memory (within run) · (19) eval parallelism/throughput · (20) edit-size budget. Each time N grew, every earlier candidate was revisited on the new axes (§4.2). |
| **T** (trees) | 7 independent search trees, each run as a separate agent that never saw the others: **O**=T1 optimization (held-out val) · **R**=T2 RL (sample efficiency) · **$**=T3 cost ($/run, $/pt) · **E**=T4 eval/assurance (hacking, gap) · **T**=T5 agent tooling (setup and use) · **A**=T6 adjacent fields (compilers, AutoML, game AI, OR, program synthesis) · **S**=T7 OSS scout (16 repos cloned; source, issues and PRs read). A config-formats probe [CF] supplied facts only and proposed no candidates. |
| **M** (outcomes) | Every candidate is scored on: valset score · sample efficiency · cost · train/val gap · implementation effort (1 = hours … 5 = weeks) · evidence strength. |

**Procedure:**
1. Each tree proposed ≥4 candidates as points on N and scored them on M, filling the T×M cells. `?` means unknown, with the reason stated.
2. N was expanded and all earlier candidates were revisited.
3. The best candidate per region was kept (§4.3).
4. Trees were merged without averaging away disagreements (§5).

**Scales:** O, R, $ and S use +/− relative to baseline (S's sign is the direction the quantity moves); A uses arrows; E and T use 1–5 with 5 = good. T's effort score was inverted to 6−x so all efforts mean the same thing. Each cell keeps its tree's own scale.

**Code state:** trees T1–T5 audited the **pre-upgrade** code. The branch now has these as flags whose defaults keep the old behaviour, pending A/B (repo `CLAUDE.md`, and S's read of the working tree): `promotion=paired_se`, `val_eval=halving`, `prescreen`, `counterexample_mining`, `mutation_operator=rewrite|section_edit|compress`, `operator_bandit`, `testset`, `EvaluationError`, `cache_evals`, `resume_from`. `use_merge` is still unused (S).

### 5.1 D6: GEPA's exact dominance and sampling rule
**Source:** [`src/gepa/gepa_utils.py` @ ce5b0d6, L54–135](https://github.com/gepa-ai/gepa/blob/ce5b0d6e3d6af6c6dbec6de2c54536bbb961d309/src/gepa/gepa_utils.py#L54-L135), fetched and read in full on 2026-11-11.

**Inputs:**
- `fronts`: for each val example id, the set of programs tied at the best score on it.
- `scores[p]`: each program's aggregate valset score.

**`remove_dominated_programs`:**
1. `remaining[key] = len(fronts[key])`.
2. Sort every program on any front by `scores`, lowest first. The sort is stable (first-seen order on ties).
3. Make **one pass**. Mark y dominated if every key whose front contains y has `remaining[key] > 1`; when you do, decrement those keys.
4. Return the fronts without dominated programs. Every non-empty front keeps ≥1 program (asserted).

**`select_program_candidate_from_pareto_front`:**
- `freq[p]` = number of pruned fronts containing p.
- Build a list with each p repeated `freq[p]` times, in first-seen order.
- Return `rng.choice(list)`. There is no fallback (an empty list is an assertion error).

**Where the branch's subset rule differs:**
1. A on {k1,k2}, B on {k1}, C on {k2}, A lowest score: GEPA removes A; the branch keeps it.
2. Two programs with identical key sets: GEPA removes the lower-scored one; the branch keeps both.
3. Sampling order: the branch builds its list in sorted-pid order, so the same seed picks differently.

**Test:** random fronts and scores, asserting the pruned fronts match.

**Not disagreements (none invented):**
- **Merge:** O and R agree it should be opt-in.
- **Opus vs Fable:** only $ takes a position (Opus default, Fable in the quality preset).
- **Section edits:** O, A and $ all favour them and nobody argues against, but the evidence is `abstract-only`, so A/B.
- **CEGIS from train/dev only:** matches E's split rule.
